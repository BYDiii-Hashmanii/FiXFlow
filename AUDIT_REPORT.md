# FixFlow independent audit

## 1. Executive summary

| Frontend | Backend | Database | AI service | Integration | Security | UX |
|---|---|---|---|---|---|---|
| 5/10 | 3/10 | 5/10 | 4/10 | 3/10 | 1/10 | 4/10 |

Scores are engineering judgments on a scale where 10 means ready for production. The UX score reflects source review. Browser layout and live workflow results remain unverified unless expressly noted.

1. Login, registration and token validation can grant an existing identity without proving the user owns it (C01–C02).
2. Core request, job, invoice and owner routes omit access checks or return company-wide data without tenant scoping (C03–C04).
3. The payment screen closes jobs and issues receipts based on an unverified payment selection (C05).
4. Technician accept and decline are browser-only. Customers can wait indefinitely, and separate job operations can create an accepted job as a side effect (H01–H02).
5. Customer tracking loses lifecycle states and links to a fixed invoice. A successful booking can still show the wrong job or bill (H03–H04).

This was a read-only review of source and the supplied SQLite database. Flow ratings describe demonstrated source behavior. No application records were created or modified. References below use **B** = `Fyp_Backend/app` and **F** = `Fyp_frontend/src/app`. Line ranges identify the reviewed code.

The observed table names, core columns, uniqueness and FK declarations align with the ORM. SQLite has no enum CHECK constraints for the VARCHAR-backed enums, no server column defaults, no application sequences, and no views or triggers. Python defaults and on-update behavior are in the ORM. `design.py` is PostgreSQL SQL used as a design reference. Its native enums, number sequences, CHECKs, server defaults, triggers, composite indexes and three views are absent in the live SQLite file (B/database/design.py:18–43, 51–230, 235–323). Neither the app's queries nor startup reference `v_technician_stats`, `v_technician_directory` or `v_company_stats`. The equivalent application queries and formatters are in B/controllers/request_controller.py:28–51 and B/controllers/owner_controller.py:56–93. Startup enables FKs and runs `create_all` plus seed, which cannot migrate existing tables (B/database/session.py:6–17, B/database/seed.py:6–12).

`PRAGMA integrity_check` returned `ok`; `foreign_key_check` returned zero rows. Four jobs exist, three without an accepted offer for their technician, and one paid invoice has both a payment amount different from its stored invoice total and a job still marked completed. All three invoices are paid. These are measured properties of the supplied database. The audit cannot establish whether a manual action, seed or application request created any particular inconsistent row. No duplicate reviews and no request/job technician mismatches were present. User ID 7 exists. There were five pending offers and one accepted offer, across three waiting requests and other lifecycle states. Notification types present were request, offer, invoice, payment and feedback. The source writes live payment and feedback events only.

### Business rules and transaction boundaries

The following table enumerates write paths with missing preconditions. Set notation covers every source-permitted state for each path. The allowed states in the final column are proposed policy, subject to deciding whether cancellation after booking needs a separate exception workflow. Assignment and tenant requirements are covered in C03–C04.

| Operation | Source-permitted transition or side effect | Required precondition |
|---|---|---|
| Send/re-send offer | Every request state can be overwritten to waiting and reassigned, including waiting, accepted, in progress, completed, closed paid, self-solved and cancelled. An existing accepted/declined offer for that technician can be reset to pending, other pending offers remain, and an existing job survives. B/controllers/request_controller.py:334–365 | Customer owns a bookable or retryable request. One live offer or an explicit competing-offer policy. Reject after assignment or closure. |
| Solve or cancel | Every request state can be overwritten to solved_by_customer or cancelled, including waiting, accepted, in progress, completed, closed_paid, each terminal state and the same state. Jobs, offers and invoices remain unchanged. Missing record can still yield success. B/controllers/request_controller.py:314–321; B/routes/request_routes.py:63–76 | Self-solve before work is assigned. Define cancellable states and reconcile pending offers in the same transaction. |
| Accept or decline | No server transition. A job may instead appear as accepted from any request state on generic job lookup, with no offer decision. B/controllers/job_controller.py:163–185 | Assigned technician must decide a still-pending offer once. Acceptance creates a job and updates the request in one commit. Decline records reason and releases the request for rebooking. |
| Start | Any job goes to in_progress. Repeated start overwrites the timestamp, and completed/closed jobs reopen. The request moves to in_progress regardless of its prior state. B/controllers/job_controller.py:91–98 | Only accepted can start. Retrying an already-started request returns the original start state. |
| Update work | Any job, including accepted, completed and closed, can have work and costs replaced. Fetched request-only records may first create a job. B/controllers/job_controller.py:100–124, 163–185 | Only in-progress work is mutable. Issued amounts and parts are immutable. |

| Issue or reissue invoice | Any job state can get a new unpaid invoice. Any existing invoice, including draft, unpaid and paid, can have totals and sent time replaced while retaining its status. B/controllers/job_controller.py:135–161 | Only completed jobs. Publish a finalized snapshot once or apply an explicit adjustment policy. |
| Pay | Any invoice status, including draft or paid, can become or remain paid. Every job linked to it can move to closed, and every associated request can move to closed_paid. | Review | A first review can be added for any job state, including from a lookup-created job, by any resolved user, with an unbounded integer rating. Controllers duplicate list filtering and response assembly across request, job, invoice and owner paths. Review handling writes business data directly in the route, while the job lookup both resolves and mutates records (B/controllers/request_controller.py:54–97, 260–281, B/controllers/job_controller.py:11–68, 163–185, B/controllers/owner_controller.py:11–49, 151–196, B/routes/job_routes.py:50–88). Centralize state changes and scoped queries before consolidating the role-specific response models. The persisted offer decline reason and response timestamp are not maintained by a live decision path, and job photo persistence is absent (B/database/models.py:193–208, 248–258; B/controllers/request_controller.py:349–365).

Technician creation adds the user, flushes to get its key, adds the technician and commits once (B/controllers/owner_controller.py:105–126). Request creation likewise commits request, analysis and repair steps together, but disk write occurs first (B/controllers/request_controller.py:123–137, 211–258). Start, complete, invoice generation and review use additional commits if their job lookup first creates a row. Payment currently commits payment, invoice, job, request and notification together. Its issue is validation, atomic competition for the transition and repeat behavior. The current review and payment unique constraints protect against a second durable row. Concurrent behavior and exact SQLite error mode remain unverified. The scoped acceptance transaction is absent. Only the technician-per-request uniqueness rule is imposed on offers, which permits multiple pending offers for different technicians.

Auth uses bcrypt with a random salt, but silently truncates at 72 UTF-8 bytes (B/middlewares/security.py:6–15). Validate length or adopt a migration-compatible hashing strategy. Login and registration schemas permit weak or missing passwords, and no app-level rate limiter was found in auth routing or middleware configuration (B/api/schemas/auth_schemas.py:1–32, B/routes/auth_routes.py:12–22, B/main.py:49–64). Add identifier/IP throttling with generic authentication errors. Password hashes are stored in SQLite and excluded from the reviewed user serializer (B/database/models.py:75–97, B/controllers/auth_controller.py:18–28). Queries reviewed use ORM-bound parameters, including the fuzzy email lookup, so no raw SQL injection was established. Fuzzy matching is an identity-selection flaw.
